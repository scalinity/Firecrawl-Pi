# RESTORE
Disaster recovery for the Firecrawl Pi Platform (FIRECRAWL_PI_SPEC.md §26). Printed by `fcpi help restore`.

What you need, none of it on the Pi:
  - the backup repository's address and its backend credentials (the owner's record of /etc/firecrawl-pi/backup.env);
  - the repository's recovery key, a restic key the owner holds apart from the repository and the Pi;
  - a copy of this Git repository (the deployed commit is recorded in every snapshot's backup-meta.json).

1. On the replacement host: Debian 13 arm64 with Docker Engine and the compose plugin, restic and jq; the project's user
   IDs (scripts/m1/pi-init.sh) and a data filesystem for /srv/firecrawl-pi. Do not start the stack yet.
2. Point restic at the repository with the recovery key:
     export RESTIC_REPOSITORY=<repository>; export RESTIC_PASSWORD_FILE=<file holding the recovery key>
     restic snapshots --tag fcpi-data          # choose the run: the newest unless it is known bad
3. Restore the run's two snapshots into an empty directory:
     restic restore <data snapshot> --target /srv/firecrawl-pi/recover
     restic dump <secrets snapshot of the same run> fcpi-secrets.tar | tar -C /etc/firecrawl-pi -xpf -
   Check the copy: (cd /srv/firecrawl-pi/recover/srv/firecrawl-pi/backup-staging/current && sha256sum -c MANIFEST.sha256)
4. Put the state in place (as root, preserving owners):
     mv  .../backup-staging/current/data/{postgres,redis,rabbitmq,.fcpi-data-id}  /srv/firecrawl-pi/data/
     mv  .../srv/firecrawl-pi/data/artifacts  /srv/firecrawl-pi/data/
     cp -a .../etc/firecrawl-pi/.  /etc/firecrawl-pi/    (config.env, selection, egress lists; the secrets came in step 3)
   Set PI_DATA_MOUNT_ID in /etc/firecrawl-pi/config.env to the new filesystem's UUID.
5. Deploy the commit backup-meta.json names (scripts/m1/deploy.sh from the workstation) and run the milestone init
   scripts in order (scripts/m1/pi-init.sh ... scripts/m8/pi-init-m8.sh). They keep every existing secret and data
   directory. Images: the project's own images are rebuilt from that commit (scripts/m2/build-api-image.sh on the
   workstation, the pi-build-images scripts on the host); public images are pulled by the digests the version lock holds.
6. Before starting: keep paid dispatch off (PI_PAID_DISPATCH_ENABLED=false) and webhook delivery suppressed
   (deploy/compose.webhooks-suppressed.yaml) until provider spend newer than the backup is reconciled and the owner
   has confirmed that no webhook sent after the backup would be sent twice. Then: systemctl start fcpi-stack.
7. Prove it: fcpi verify ops; fcpi verify functional; fcpi status. Jobs acknowledged after the backup's time are not
   in it: the recovery point is the backup's time (at most a day, spec §26).
8. Take a new backup at once (fcpi backup), so the repository holds the recovered host's own first snapshot.
# END RESTORE
